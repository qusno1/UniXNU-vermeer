The image carries BootShim, the 3 MiB firmware volume and the stock ABL device
tree. It has no payload volume, so the menu has no boot entry.

## Command

```sh
fastboot boot boot.img
```

The bootloader reported:

```
Sending 'boot.img' (1788 KB)                       OKAY [  0.045s]
Booting                                            OKAY [  0.078s]
Finished. Total time: 0.126s
```

Nothing was written to any partition. The host has no `adb` or `fastboot`
device afterwards, which is expected: the firmware replaces the Android and
fastboot USB stacks, and this board has no UART.

## Observed

The screen shows the UniXNU menu with its `UNIXNU:` output.

## What this establishes

- The Android bootloader accepts the image: the v0 container, the ARM64
  `BootShim` header and the 3 MiB firmware volume at `0xa7100000`.
- `BootShim` hands control to the firmware volume and `SEC` reaches DXE.
- The memory map from `MemoryMapLib` and `VermeerBootMemoryDxe` is sufficient
  for the firmware to run: no stall at `MMU: enabled`, which the reference
  platform hit before `PcdBuildXblHobs` was turned off.
- `SimpleFbDxe` publishes a GOP the boot manager can draw on. The
  1440x3200x32 frame-buffer PCDs from this board's panel timing are usable, and
  the previous stage's scanout is preserved without the splash node being
  re-added (the stock device tree already carries it).
- `UniXNU.efi` runs from the firmware volume and starts its application,
  configuration and menu path.

## Not established

- No payload, kernel, ADT or root: the image has an empty ramdisk, so stages 3
  (payload), 4 (loader handoff), 5 (kernel entry), 6 (root mount) and 7
  (launchd) are untested.
- No log beyond the screen. The firmware log export is not wired, so no text
  transcript exists.
- Nothing was measured about interrupts, timers or secondary CPUs under the
  firmware beyond the menu appearing.
